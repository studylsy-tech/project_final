# 📢 팀 프로젝트: 문의하기(Contact) 기능 긴급 점검 및 기술 가이드

현재 공유된 문의하기 기능의 코드 검토 결과, 단순 게시판 등록 수준에 머물러 있어 **실시간 관리자 메일 알림**이라는 본래의 기획 의도를 충족하지 못하고 있습니다. 이에 따른 문제점 분석과 기술적 해결 방향을 정리합니다.

---

### 1. 현황 분석 및 문제점 (Current Issues)

현재 코드는 서버 측의 메일 발송 로직이 결여된 '반쪽짜리' 상태입니다.

* **메일 발송 엔진 부재**: footer.jsp의 메일 링크는 `mailto:` 방식의 단순 클라이언트 연결입니다. 이는 사용자 로컬의 아웃룩(Outlook) 등을 호출할 뿐, 우리 서버 시스템에서 자동으로 메일을 쏘는 기능이 아닙니다.
* **데이터 불일치 및 런타임 에러**: DB 관련 객체(VO, Mapper) 내의 변수명이 상이합니다. 이 상태로 빌드 및 실행 시 매핑 오류로 인한 데이터 저장 실패(Internal Server Error)가 명확합니다.

---

### 2. 코드 최적화 및 정리 (Refactoring)

불필요한 리소스 낭비와 논리적 충돌을 방지하기 위해 다음 항목을 정리합니다.

* **SQL 가용성 확보**: 스크립트 내 `DROP` 구문을 제거합니다. 테이블을 매번 초기화하는 방식은 실무에서 매우 위험하므로 데이터 보존을 위해 `CREATE` 문 중심으로 관리합니다.
* **변수 단일화 (Normalization)**: 용도가 중복되는 `status`와 `is_answered` 변수를 하나로 통합합니다. 데이터 정규화를 통해 로직의 복잡도를 낮추고 유지보수성을 높입니다.

---

### 3. 메일 발송 엔진 복구 (Core Engine Recovery)

과거 성공적으로 구현했던 **Jakarta Mail API** 기반의 로직을 프로젝트 구조에 재이식합니다.

| 핵심 구성 요소 | 역할 설명 |
| :--- | :--- |
| **gmail.properties** | 실제 발송용 구글 계정 및 앱 비밀번호(App Password) 설정 |
| **GmailAuthenticator.java** | 구글 SMTP 서버와의 세션을 형성하는 인증 핵심 엔진 |
| **MailUtil.java** | 복잡한 JavaMail 로직을 캡슐화하여 Controller에서 즉시 호출 가능하게 만든 유틸리티 |

---

### 4. 향후 작업 로드맵

단순 저장(DB)에서 **알림(Push)**이 결합된 완성형 프로세스로 전환합니다.

1.  **엔진 통합**: `Authenticator`와 `MailUtil`을 현재 프로젝트 라이브러리에 병합합니다.
2.  **트랜잭션 설계**: Controller 내에서 `문의 데이터 DB 저장` 성공 직후, `메일 발송 함수`가 연쇄적으로 실행되도록 로직을 수정합니다.
3.  **최종 결과**: 사용자가 웹 사이트에서 문의를 제출하는 즉시, 관리자의 실제 메일함으로 알림이 전송되는 구조를 완성합니다.
